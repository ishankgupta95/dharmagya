## A. Privacy manifest (PrivacyInfo.xcprivacy)

### A.1 What is generated automatically

1. **Expo prebuild** (`@expo/config-plugins` `IOSConfig.PrivacyInfo.withPrivacyInfo`, in `withDefaultPlugins`): only if `expo.ios.privacyManifests` is set, it writes/merges `ios/<project>/PrivacyInfo.xcprivacy` and adds it to the app target's Resources build phase (`node_modules/@expo/config-plugins/build/ios/PrivacyInfo.js`; merge dedupes reasons/purposes/domains; `NSPrivacyTracking` is overwritten by the value you give). Docs: https://docs.expo.dev/guides/apple-privacy/ (schema: https://docs.expo.dev/versions/latest/config/app/ → `ios.privacyManifests` with `NSPrivacyAccessedAPITypes`, `NSPrivacyTrackingDomains`, `NSPrivacyTracking`, `NSPrivacyCollectedDataTypes`).
2. **RN 0.86 `pod install` aggregation** (`privacy_file_aggregation_enabled: true`, which `Podfile.properties.json` enables): `PrivacyManifestUtils.add_aggregated_privacy_manifest` (a) finds or creates `PrivacyInfo.xcprivacy` next to Info.plist, defaulting to `NSPrivacyCollectedDataTypes: []`, `NSPrivacyTracking: false`; (b) adds RN core's required-reason APIs: **FileTimestamp C617.1, UserDefaults CA92.1, SystemBootTime 35F9.1**; (c) merges `NSPrivacyAccessedAPITypes` from every pod whose podspec exposes `PrivacyInfo.xcprivacy` in `resource_bundles`; (d) ensures the file is referenced by the app target. It does NOT touch `NSPrivacyCollectedDataTypes` / tracking keys beyond what already exists in the file.
3. **Expo pods that ship manifests and are picked up by (c)** (all use `resource_bundles`):
   - expo-application: FileTimestamp `C617.1`
   - expo-constants: UserDefaults `CA92.1`
   - expo-notifications: UserDefaults `CA92.1`
   - expo-localization: UserDefaults `CA92.1`
   - expo-file-system: FileTimestamp `0A2A.1`, `3B52.1`; DiskSpace `E174.1`, `85F4.1`
   (`node_modules/<pkg>/ios/PrivacyInfo.xcprivacy` + `.podspec`).
4. **Google Mobile Ads SDK / UMP**: they are vendored **static** xcframeworks (`file` on the cached 13.1.0 binary → "current ar archive"), so their `PrivacyInfo.xcprivacy` lives inside `GoogleMobileAds.framework` / `UserMessagingPlatform.framework`, not in a pod resource bundle → **RN's aggregation does not merge their required-reason entries**. Apple's processing is supposed to read static-framework manifests (Apple: "If you distribute your third-party SDK as a static library, use the support for static frameworks in Xcode 15 or later to bundle resources, including the privacy manifest file" — https://developer.apple.com/documentation/bundleresources/privacy-manifest-files), and Google states "Google Mobile Ads SDK version 11.2.0 and higher supports privacy manifest declarations" (https://developers.google.com/admob/ios/privacy/data-disclosure). Expo warns "Apple does not correctly parse all the PrivacyInfo files included by static CocoaPods dependencies" (https://docs.expo.dev/guides/apple-privacy/). **Mitigation: duplicate Google's three required-reason entries at app level** (dedup-safe).
   - Contents of the cached **GMA 13.1.0** manifest (`~/Library/Caches/CocoaPods/Pods/Release/Google-Mobile-Ads-SDK/13.1.0-8429b/.../PrivacyInfo.xcprivacy`; re-read 2026-09-23 with `plutil`. With the library pinned at 16.3.4 this **is** the version the iOS build links, so no extrapolation is needed any more): accessed APIs **SystemBootTime 35F9.1, UserDefaults CA92.1, DiskSpace E174.1**; collected types: OtherDiagnosticData (linked no / tracking no), **CoarseLocation (linked YES / tracking no)**, PerformanceData (no/no), CrashData (no/no, Analytics), **AdvertisingData (linked YES / tracking no)**, **ProductInteraction (linked YES / tracking no)**, **DeviceID (linked YES / tracking YES)**. Purposes: ThirdPartyAdvertising, DeveloperAdvertising, Analytics. **No `NSPrivacyTracking` key and no `NSPrivacyTrackingDomains` in Google's manifest.**
   - **UMP 3.1.0** manifest (re-read 2026-09-23): CoarseLocation, PerformanceData, ProductInteraction (all linked no / tracking no, purpose AppFunctionality); UserDefaults CA92.1. No `NSPrivacyTracking` key.

### A.2 What the app-level manifest must declare

- Apple: "Your app's privacy manifest file doesn't need to cover data collected by third-party SDKs that your app links to" and "If you use the API in your app's code, then you need to report the API in your app's privacy manifest file" (https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests, https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api). Since May 1 2024 uploads without reasons are rejected (https://developer.apple.com/news/upcoming-requirements/).
- The app's own JS/native code sends nothing off-device (no analytics, no crash SDK) → **`NSPrivacyCollectedDataTypes` at app level: empty**.
- **UserDefaults CA92.1 for a custom native module / App Group**: not applicable today — there is no iOS native module and no App Group in the repo (see §0). If the WidgetKit pass lands: add `1C8F.1` (app-group-shared UserDefaults; secondary confirmation only — I could not extract Apple's per-code text from the JS-rendered page: https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) alongside `CA92.1`, and `com.apple.security.application-groups` (EAS App Groups sync "require[s] Apple cookies authentication (running locally)" — https://docs.expo.dev/build-reference/ios-capabilities/).
- File timestamp / disk space / boot time: RN core + Expo pods cover `C617.1`, `0A2A.1`, `3B52.1`, `E174.1`, `85F4.1`, `35F9.1` via aggregation; Google's `35F9.1`/`CA92.1`/`E174.1` are duplicated at app level as mitigation.
- **`NSPrivacyTracking`**: keep `false` at app level in **both** ATT choices. Reason: the tracking (IDFA use) is performed by Google's SDK, which per Apple must be declared in the SDK's own manifest (Google declares DeviceID tracking=true but not `NSPrivacyTracking`/domains). Apple: "When set to true you need to provide a list of internet domains in NSPrivacyTrackingDomains" and "If the user has not granted tracking permission ... network requests to these domains fail" (https://developer.apple.com/documentation/bundleresources/privacy-manifest-files). Google support repeats the same rule and supplies **no** domain list (https://groups.google.com/g/google-admob-ads-sdk/c/bXq0Ex-o06w). Listing Google ad domains as tracking domains would make ad requests fail for every user who denies ATT. **Unverified**: whether App Review ever asks an app whose SDK tracks to flip the app-level flag; I found no Apple statement requiring it. The tracking disclosure belongs in the App Store Connect labels (§B).

## B. App Privacy "nutrition label" draft

Definitions (https://developer.apple.com/app-store/app-privacy-details/): "collect" = "transmitting data off the device in a way that allows you and/or your third-party partners to access it for a period longer than what is necessary to service the transmitted request in real time"; "Data that is processed only on device is not 'collected'"; "If you use third-party code, such as advertising or analytics SDKs, you must describe what data it collects, how it is used, and whether it tracks users" (https://developer.apple.com/app-store/user-privacy-and-data-use/). Google's own list of what the GMA SDK may collect: "IP address ... may be used to estimate the general location of a device", crash logs, performance data, "advertising identifier or other app- or developer-bounded device identifiers", "advertisements the user has seen", "app launch taps ... video views" (https://developers.google.com/admob/ios/privacy/data-disclosure). Purposes below follow Google's own manifest (§A.1.4).

### B.0 Decided: option (b) — the answers to enter in App Store Connect (2026-09-23)

The product page groups collected data under "Data Used to Track You", "Data Linked to You" and "Data Not Linked to You" (plus "Data Not Collected" when nothing is). There is no separate "not used to track you" section: under (b) the answer to "Is this data used for tracking purposes?" is **No for every data type**, so the "Data Used to Track You" section simply does not appear. "Data Not Collected" is not available to us — the Google Mobile Ads (GMA) SDK and UMP are compiled in and send data off-device (§A.1.4), and Apple requires third-party SDK collection to be declared.

Per-type answers. Source for every linked / purpose value is Google's own privacy manifests for the exact SDK versions this build links (GMA 13.1.0, UMP 3.1.0 — §A.1.4, re-read 2026-09-23). Apple takes one "linked" answer per data type, so a type that GMA declares linked and UMP declares not-linked is answered linked, with the purposes merged.

**Why the four ad types are not under "Data Not Linked to You".** Google's published App Store guidance (https://developers.google.com/admob/ios/privacy/data-disclosure, fetched 2026-09-23) lists *what* the SDK may collect (IP-derived location, crash logs, performance data, device identifiers, advertising data, user interactions) but says nothing about linkage or tracking; it points to the SDK's privacy-manifest declarations, and those mark Coarse Location, Device ID, Advertising Data and Product Interaction as **linked**. Non-personalised ads do not change that: Google states NPA ads still use mobile ad identifiers for frequency capping and aggregated reporting (https://support.google.com/admob/answer/7676680). **No Google source supports "not linked" for those four types under NPA — not verified, do not declare them as Not Linked.** Xcode → Archive → Generate Privacy Report aggregates the same manifests, so these answers also match what that report shows.

**Risk (not verifiable before review).** GMA's manifest declares Device ID `tracking = true` unconditionally, so the archive's privacy report will say Device ID is used for tracking, while the label says no. The "No" rests on: no ATT request → IDFA all zeros (Apple); `npa=1` on every iOS request → no cross-app ad targeting; Apple defines tracking as linking app data with third-party data for targeted advertising *or advertising measurement*, or sharing it with data brokers. Google's NPA frequency capping and aggregated reporting could be read as "advertising measurement", so this is a grey area. If App Review insists Device ID is tracking, (b) stops being viable as built: declaring tracking requires the ATT prompt, i.e. option (a). Suggested App Review note: "The app never requests tracking authorization. All iOS ad requests are non-personalised (npa=1)."

## D. App Tracking Transparency

> **Decided 2026-09-23: option (b)** — no ATT prompt, non-personalised ads only on iOS, "no tracking" label (§B.0). Implementation and the one console rule it depends on are in §D.1 and §D.2; the research below is kept as the basis for the decision.

- Apple rules (https://developer.apple.com/app-store/user-privacy-and-data-use/): "In iOS 14.5 ... you need to receive the user's permission through the App Tracking Transparency (ATT) framework in order to track them or access their device's advertising identifier"; "Unless you receive permission ... the device's advertising identifier value will be all zeros and you may not track them"; SDK example: "Placing a third-party SDK in your app that combines user data from your app with user data from other developers' apps to target advertising ... even if you don't use the SDK for these purposes"; "Can I gate functionality on agreeing to allow tracking ...? No, per ... 5.1.2(i)". Guideline 5.1.2(i): "You must receive explicit permission from users via the App Tracking Transparency APIs to track their activity. Your app may not require users to enable system functionalities (e.g. push notifications, location services, tracking) in order to access functionality" (https://developer.apple.com/app-store/review/guidelines/). HIG: "Avoid requesting permission at launch unless the data or resource is required for your app to function" (https://developer.apple.com/design/human-interface-guidelines/privacy).
- **App Store Connect answer**: per data type you answer whether it is "used for tracking"; (a) → Device ID: yes; (b) → no tracking. The ATT prompt is not required unless you track/access IDFA (Apple text above).
- **UMP can run the whole flow**: create an IDFA message in AdMob Privacy & messaging, add `NSUserTrackingUsageDescription`; "The ATT alert appears only once per installation"; "If a user denies ATT consent, you can still request ads, but the Google Mobile Ads SDK will not send the IDFA" (https://developers.google.com/admob/ios/privacy/idfa; explainer→"Continue"→system alert flow: https://support.google.com/admob/answer/10115027). Library: "If you configure an ATT message in your Google AdMob account, the UMP SDK will automatically handle the ATT alert. This will also show an IDFA explainer message" (`docs/european-user-consent.mdx`; https://docs.page/invertase/react-native-google-mobile-ads/european-user-consent). So `gatherConsent()` in `adsConsent.ts` would cover (a) with only a console + `userTrackingUsageDescription` change (plus dropping the iOS NPA flag in `src/config/ads.ts`) — which is also exactly why, under the chosen (b), the console message must never be published (§D.2). Manual alternative: `expo-tracking-transparency` `requestTrackingPermissionsAsync()` before `mobileAds().initialize()` (`docs/index.mdx`; https://docs.expo.dev/versions/latest/sdk/tracking-transparency/). Google: "it's recommended to wait for the completion before loading ads" (https://developers.google.com/admob/ios/ios14).
- **(b) mechanics** (implemented — §D.1): pass `requestOptions: { requestNonPersonalizedAdsOnly: true }` on `BannerAd` and `InterstitialAd.createForAdRequest(unitId, {...})` for iOS; native side sets `npa=1` extras (`ios/RNGoogleMobileAds/RNGoogleMobileAdsCommon.mm` L56–58; Android twin `ReactNativeGoogleMobileAdsCommon.java` L157–159). The SDK has no global NPA switch reachable from JS (`RequestConfiguration` exposes only content rating, child/under-age tags and test devices), so it has to be per request. SKAdNetwork attribution still works without IDFA ("attribute an app install even when the IDFA is not available" — https://developers.google.com/admob/ios/privacy/strategies).
- **Trade-off numbers (secondary sources, treat as ranges)**: global ATT opt-in ≈ 35% (Q2 2025) → ≈ 38% (Q1 2026) per Adjust (https://www.adjust.com/blog/att-opt-in-rates-2025/, https://www.businessofapps.com/data/att-opt-in-rates/); no India-specific figure found. Non-personalised/unconsented iOS traffic earns "20 to 40 percent lower eCPMs" (https://www.adnimation.com/mobile-optimization-in-2025-turning-every-tap-into-revenue/) up to "60–80% less" (https://www.monetizemore.com/blog/admob-monetization/) — vendor blogs, not Google data. iOS is ≈ 4–7% of India mobile OS share (StatCounter via secondary summaries; https://gs.statcounter.com/os-market-share/mobile/india — could not fetch the page directly).
- **Recommendation (adopted 2026-09-23): ship v1 with (b)** — no ATT prompt, NPA on iOS, "no tracking" label, no `NSUserTrackingUsageDescription`. Rationale: iOS is a single-digit share of an India-centric audience, so the incremental revenue of (a) ≈ (opt-in ≈ 35–40%) × (personalised premium) × (small iOS base) is minor against: an extra system prompt, a "Device ID – tracking" label on a devotional app, stricter review, and the privacy-policy rewrite. (a) can be switched on later with a console change + plugin option + label update (needs a new build and label resubmission). If revenue data later justifies it, prefer the UMP IDFA-explainer route so the prompt is contextual and not at launch.

### D.2 Caveat: never publish an IDFA explainer / ATT message for the iOS app

In AdMob → Privacy & messaging, publish GDPR / US-state messages for the iOS app as needed, but **do not create or publish an "IDFA explainer" (ATT) message for it**. Evidence:

- **UMP runs ATT itself when that message exists.** Library docs: if an ATT message is configured in AdMob, UMP handles the ATT alert automatically and also shows the IDFA explainer, and a tracking usage description must be provided (`node_modules/react-native-google-mobile-ads/docs/european-user-consent.mdx`, "App Tracking Transparency"). The UMP 3.1.0 binary this build links (`~/Library/Caches/CocoaPods/Pods/Release/GoogleUserMessagingPlatform/3.1.0-befe6/…/UserMessagingPlatform`, `strings`) references `ATTrackingManager`, `requestTrackingAuthorizationWithCompletionHandler:`, `trackingAuthorizationStatus`, `requestIDFAConsent` and `NSUserTrackingUsageDescription`. `adsConsent.ts` calls `AdsConsent.gatherConsent()`, which is the call that would present it.
- **iOS kills an app that calls ATT without the key.** Apple's `NSUserTrackingUsageDescription` reference (fetched 2026-09-23) says the key is required and an app using the ATT framework without it crashes. Google's IDFA page (https://developers.google.com/admob/ios/privacy/idfa) likewise has you add the key before the message is shown.
- **Not verified**: whether UMP 3.1.0 checks for the key and skips the ATT call when it is missing (the binary references the key name, which could be a guard or just the prompt text), and whether Google's servers would even serve the message to a build without it. Treat the crash as the real risk. It cannot happen today (the iOS build still uses Google's sample app id, so none of the owner's messages reach it); it becomes live the day the real iOS app id is pasted.
- **Switching to (a) later** needs all three together, in one build: the IDFA message in AdMob, `userTrackingUsageDescription` on the ads plugin in `app.json`, and `AD_REQUEST_OPTIONS` → `undefined` on iOS in `src/config/ads.ts`; plus relabelling Device ID as used for tracking.
