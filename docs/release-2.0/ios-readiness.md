## 6. Fonts

**The iOS font gap is closed in the working tree (uncommitted).** Mechanism, verified end-to-end:

1. `app.json` `expo-font` plugin embeds the 7 TTFs for **Android only** (no `ios` key), so Android resolves `fontFamily` by asset basename; iOS gets no `UIAppFonts` (confirmed: none in generated `Info.plist`).
2. `src/config/fontGate.ts` (Android + tsc target) returns `true`; Metro picks `src/config/fontGate.ios.ts` on iOS and `fontGate.web.ts` on web, both re-exporting `src/config/fontGate.runtime.ts:22-30,38-48`, which calls `useFonts` with keys equal to the family strings (`Geist_200ExtraLight`…`NotoSerifDevanagari_600SemiBold`) and subpath `require`s (no root-package import). Resolves `true` on error too (no splash hang).
3. `app/_layout.tsx:48` imports `useAppFonts`; `:314-315` gates `appReady = storeHydrated && fontsReady`; `:326-330` hides the splash only after `appReady`, and the `(tabs)` tree mounts after that.
4. iOS resolution: expo-font registers each face under its PostScript name and aliases the requested key via a swizzled `UIFont.fontNames(forFamilyName:)` (`node_modules/expo-font/ios/UIFont+FontFamilyAlias.swift:6-27`); React Native's `RCTFont` and react-native-screens' tab-bar label path (`node_modules/react-native-screens/ios/tabs/RNSTabBarAppearanceCoordinator.mm:240` uses `RCTFont updateFont`) both go through it, so `NativeTabs labelStyle.fontFamily` (`app/(tabs)/_layout.tsx:67-68`) resolves as well.

**Recommendation: keep the runtime `useFonts` gate (current design) over PostScript-name mapping.** PostScript names (`Geist-Regular`, `NotoSerifDevanagari-Medium`, …) differ from the Android asset basenames, which would force platform-specific strings in every one of the files below; the alias approach keeps one vocabulary. Cost is a few ms of asset registration per cold start (bundled assets, no network). ## 7. Ads on iOS

**Verdict: no request is ever attempted on iOS, no consent form is shown, banners collapse to `null`, nothing crashes. Revenue on iOS is zero until real ids land. When they land, every iOS request is already non-personalised (ATT option (b), decided 2026-09-23).**

- **ATT decision (b), implemented 2026-09-23.** No App Tracking Transparency prompt; iOS serves non-personalised ads only. `src/config/ads.ts` holds the one decision point, `AD_REQUEST_OPTIONS` = `{ requestNonPersonalizedAdsOnly: true }` on iOS (→ `npa=1` in `RNGoogleMobileAdsCommon.mm` L56–58) and `undefined` on Android. For code that reaches the SDK through `getAdsModule()`, the only ways to request an ad are `renderBannerAd()` (used by `AdBanner`) and `createInterstitialAd()` (used by `interstitialAds.ts`); both attach it, and `getAdsModule()`'s return type withholds the SDK's request constructors (`BannerAd`, `InterstitialAd`, rewarded / app-open / native / GAM variants, request hooks), so such a call site cannot skip the flag without a `tsc` error. **Gap:** that is a type on `getAdsModule()`, not a fence around the package — a direct value import of `react-native-google-mobile-ads` in any other file (`import { BannerAd } from …`) type-checks and lints cleanly and would send iOS requests without the NPA flag. Today `src/config/ads.ts` is the only value importer; the `no-restricted-imports` rule that would enforce it is written out in `privacy-surface.md` §D.1 (not applied: `eslint.config.js` is outside this change).
